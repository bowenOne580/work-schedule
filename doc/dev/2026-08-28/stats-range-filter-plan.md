# 统计范围筛选方案（全局统计范围选择器）

- 日期：2026-08-28
- 状态：已实施
- 分支：dev
- 关联代码：`src/services/schedulerService.js`（#computeStatistics / getStatisticsOverview）、`src/createApp.js`（/api/statistics/overview 路由）、`frontend/src/pages/StatsPage.tsx`、`frontend/src/api/index.ts`、`frontend/src/hooks/useApi.ts`

## 1. 背景与目标

统计页（`/app/stats`）当前只展示固定口径的数据：今日/本周/近 7 天。需要增加一个**全局统计范围选项**，置于页面右上角，下拉选择：

- **一周**：最近 7 天（含今日）
- **一月**：最近 30 天（含今日）
- **全部**：有史以来
- **自定义**：起止日期（从某天到某天）

切换后，页面上**所有**统计元素（6 张摘要卡、分类用时对比、优先级完成分布、每日用时趋势）按所选范围重新计算展示。

## 2. 可行性结论：好改，且无缓存失效/性能风险

用户关心"每次切换统计范围都涉及界面内部元素重算，可能使缓存失效或响应缓慢"。逐层分析后结论如下：

**① 服务端重算不是问题。** `#computeStatistics`（schedulerService.js:1124）对全部任务做**单次 O(n) 遍历**，所有指标都从任务原始字段（`finishedAt`、`actualMinutes`、`estimatedMinutes`、`deadline`、`categoryId`、`manualPriority`）实时推导。单用户规模（几十~几百条任务）一次遍历耗时微秒级；即使任务到万条也在 10ms 以内。任意时间范围的计算与现有固定窗口的计算成本完全相同——只是把窗口边界从写死的"今天/本周"换成参数。

**② 不存在"历史数据没存"的问题。** 关键发现：每日用时的 `historyMap` 每次计算都**从全部 done 任务的 `finishedAt` 现场重建**，`dailyHistory` 只是它的 7 天切片，并不是滚动丢失的缓存。因此"全部/自定义"范围可以直接重放，无需任何数据迁移或补录。

**③ 缓存失效是伪问题，两层缓存都不受影响：**

| 缓存层 | 现状 | 范围切换时 |
| --- | --- | --- |
| 服务端持久化快照 `data/statistics_cache.json` | 每次**写入**后全量重算并持久化，供仪表盘与统计页默认口径使用 | **不动它**。范围统计按请求现算（见①，成本可忽略），快照继续只服务默认口径，仪表盘零影响 |
| 前端 `useApi` 内存缓存（30s TTL，按 key 存取） | 单一 key `'stats'` | key 加入范围参数（如 `stats:week`），**每个范围各占一条缓存**——30 秒内切回刚看过的范围是零请求秒出；30 秒后过期也只是重新发一次廉价 GET |

**④ 响应链路无新增瓶颈。** 切换范围 = 一次 `GET /api/statistics/overview?range=...`；该接口本就走 `storage.runExclusive`（每请求重读 JSON 文件，几 KB 级）+ 内存计算，与现状同量级。

结论：**改造为中小型工作量（后端约 1.5h、前端约 1.5h），无数据迁移、无性能风险、无缓存设计变更**。真正需要斟酌的是各指标的范围口径（第 4 节），这是本方案的核心决策点。

## 3. 现状梳理：统计计算链路

```
任务/检查点写入 → #prepareState → #computeStatistics（O(n) 单遍历，窗口写死）
                              ↘ state.statisticsCache（持久化）
GET /api/statistics/overview → 直接返回 state.statisticsCache（不现场计算）
前端 useQuery('stats') → 一次请求 → 6 卡片 + 3 图表全部来自这一个响应
```

现有指标与时间窗口的关系（范围筛选必须逐一给出口径）：

| 指标 | 现状口径 |
| --- | --- |
| 今日用时 / 本周用时 / 今日完成 / 本周完成 | 按 `finishedAt` 落在今日/本周（`startOfLocalWeek`） |
| 每日用时趋势 | `historyMap`（全部 done 任务的 finishedAt→actualMinutes 映射）的近 7 天切片 |
| 分类用时对比 | **全量**：所有任务（含未完成）的 actual/estimated 按分类累加，无时间窗口 |
| 完成率 | **全量**：done 数 / 全部任务数 |
| 准时率 / 平均超时比 | **全量**：全部 done 任务 |
| 优先级完成分布 | **全量**：全部 done 任务按优先级计数 |

## 4. 范围语义定义（核心决策点）

### 4.1 四个选项的窗口

| 选项 | 窗口（服务器本地时区） |
| --- | --- |
| 一周 | `[今日-6天 00:00, 明日 00:00)`，滑动窗口 |
| 一月 | `[今日-29天 00:00, 明日 00:00)`，滑动窗口 |
| 全部 | `[最早任务时间, ∞)`，实际实现用 `null` 表示不限 |
| 自定义 | `[from 00:00, to 次日 00:00)`，要求 `from ≤ to`；**`to` 若为未来日期自动调整为当天**（前端日期选择器限制 + 后端防御性 clamp） |

### 4.2 各指标在范围内的口径（已评审定稿 2026-08-28）

统一原则：**"用时/完成/准时率/超时比"按任务完成日归账（`finishedAt`），与现状一致；唯一按创建时间归账的是完成率。**

| 指标 | 范围口径 | 备注 |
| --- | --- | --- |
| 范围内用时 | 范围内完成任务 `actualMinutes` 之和 | 卡片标签随范围变化（见 4.3） |
| 范围内完成 | 范围内 `finishedAt` 的任务数 | 同上 |
| 完成率 | **创建于范围内的任务**的完成率 =（创建于范围内 且 已完成）÷ 创建于范围内的全部任务 | 创建时间必须落在范围内；"全部"时退化为现有口径（done/全部任务），兼容 |
| 准时率 | **范围内完成的任务**，创建时间不限（可早于范围起点） | 按deadline 判定准时，口径不变、仅加完成窗口 |
| 平均超时比 | 范围内完成的任务（创建时间不限） | 同上；仅 estimated>0 且 actual>0 的任务参与 |
| 分类用时对比 | 范围内完成任务的 actual vs estimated 按分类汇总 | 由"全量含未完成"收窄为"范围内完成"（已定稿） |
| 优先级完成分布 | 范围内完成任务按优先级计数（已定稿） | 口径不变，仅加完成窗口 |
| 每日用时趋势 | 范围内每日（`finishedAt` 归账）；"全部"从最早完成任务日起 | "全部"跨度大时依赖 Recharts 自动抽稀 x 轴标签；>180 天可选聚合为周粒度（列为后续可选，首版不做） |

### 4.3 摘要卡片的调整（已定稿）

- **保留"今日用时"卡**：固定展示今日数据、不随范围变化，维持 6 张卡的视觉对称。
- **"本周用时"→"范围内用时"、"本周完成"→"范围内完成"**：卡片含义保留，标签中的时间范围词随所选选项动态变化，如"近 7 天用时 / 近 30 天用时 / 全部用时 / 自定义用时"。
- 摘要卡仍为 **6 张**：今日用时（固定）、范围内用时、范围内完成、完成率、准时率、平均超时比。

**边界语义**：与现状相同的"完成日归账"意味着长任务的实际用时全部记在完成当天。这是系统既有口径，本方案不改变它（改变需要按检查点/暂停记录做时间分摊，是另一个量级的需求，明确不做）。

## 5. API 设计

`GET /api/statistics/overview?range=week|month|all|custom&from=YYYY-MM-DD&to=YYYY-MM-DD`

- **不带 `range` 参数时行为与现在完全一致**（返回持久化快照）——仪表盘与现有调用零影响，向后兼容。
- `range=custom` 必须带 `from`、`to`，缺失或 `from > to` → `AppError(400, "INVALID_STAT_RANGE")`；日期格式非法同上。
- 响应体结构在现有 `StatisticsOverview` 基础上**只增不改**：新增 `range`、`rangeStart`、`rangeEnd`（回显实际窗口，便于前端展示"近 7 天"等文案），其余字段同名同义按范围计算。
- 现有持久化快照字段全部保留在默认响应中。

## 6. 后端改造

1. **`#computeStatistics` 参数化重构**（核心步骤）：签名改为
   `#computeStatistics(tasks, categories, { now, rangeStart, rangeEnd, trendFrom })`；
   窗口边界从写死改为参数；`rangeStart/rangeEnd` 为 `null` 表示不限。
   默认调用（无范围）**先跑一版现有逻辑**保证持久化快照字节级兼容（`dateKey`、今日/本周、7 天趋势、全量比率均维持现状），避免影响仪表盘；
   范围调用走参数化逻辑。两版共存于同一个纯函数（按是否传范围分支），不复制粘贴两份实现——除完成率分母外，范围版与现有版的差异仅为窗口边界。
2. **`getStatisticsOverview(range)`**：无参 → 现状返回快照；带范围 → `runExclusive` 内现场计算（复用同一读事务，避免与写入竞争），不写回快照。
3. **路由**（createApp.js）：解析并校验 query 参数，透传 service。
4. **测试**（scripts/logicTests.js 增补）：构造已知 `finishedAt` 分布的任务，断言 week/month/custom 三种范围的用时、完成数、完成率、趋势切片正确；custom 非法参数返回 400。

## 7. 前端改造

1. **选择器 UI**：页面头部 `统计分析` 标题行改为 flex 两栏，右侧放下拉（原生 `<select>` 配 Tailwind，与全站风格一致），选项：近 7 天 / 近 30 天 / 全部 / 自定义；选"自定义"时下拉旁展开两个 `<input type="date">`（起/止），两者均有效才发起请求；**结束日期的 `max` 属性设为今天，用户改选未来日期时自动校正为当天**（与 4.1 的 clamp 一致）。选择器上方或下方以小字回显当前实际窗口（用响应里的 `rangeStart/rangeEnd`）。
2. **数据层**：
   - `statsApi.overview(params)` 追加 query string；
   - `useQuery` key 改为 `` `stats:${range}:${from}:${to}` ``——30s TTL 使"切回刚看过的范围"零请求；切换瞬间用上一次数据占位（spinner 只出现在首次或 30s 过期后），避免整页闪烁。
3. **摘要卡文案**：按 4.3 实施——保留今日用时卡（固定今日数据），用时/完成两张卡的标签随范围动态变化，网格维持 6 列不变。

## 10. 风险与开放问题

| 项 | 说明 |
| --- | --- |
| 全部趋势图跨度 | 天数很大时 x 轴靠自动抽稀，可读但密；周粒度聚合列为后续可选 |
| 多标签页状态 | 范围选择存组件 state 不入 URL；如需分享/刷新保持范围，可后续把 `?range=` 同步到地址栏（可选增强，首版不做） |

已定稿决策记录（2026-08-28）：一周/一月采用滑动窗口；分类用时对比与优先级完成分布均按"范围内完成"；自定义结束日期选未来时自动调整为当天；保留今日用时卡（6 张卡，视觉对称）；完成率按创建时间归账，准时率/超时比按完成时间归账（创建时间不限）。

## 11. 后续优化：趋势图与分类图粒度自适应 + 横向滚动（2026-08-28 追加，已实施）

**问题**：趋势图固定按天粒度渲染，范围一长每天挤成细缝；分类对比图类别一多同样拥挤。

**方案**（纯前端，API 不变）：

1. **粒度自适应**（`aggregateTrend` 纯函数，输入后端每日原子数据）：

| 范围天数 | 粒度 | 对齐 | 轴标签 | tooltip 头 |
| --- | --- | --- | --- | --- |
| ≤ 31 天 | 天 | — | `MM-DD` | `YYYY-MM-DD` |
| 32 ~ 62 天 | 周 | 周一 | 周一日期 `MM-DD` | `YYYY-MM-DD 当周` |
| > 62 天 | 月 | 月初 | `YYYY-MM` | `YYYY-MM` |

2. **横向滚动**：桶数超阈值时，**视口内恰好显示阈值个桶**——列宽 = 视口宽 ÷ 阈值（`useElementWidth` 用 ResizeObserver 实测滚动视口宽度），条带总宽 = 桶数 × 列宽，外包 `overflow-x-auto`，其余靠滚动查看。趋势图阈值 7；**分类图阈值 5**（双柱较宽）。≤ 阈值时维持撑满布局。
3. **折线动画禁用**：Recharts 折线的描边入场动画在滚动条出现/布局抖动/悬停重渲染时可能被中断，路径冻结在半截（表现为"曲线断掉"但数据点仍在）。趋势线与分类柱状图均设 `isAnimationActive={false}`，并对趋势线加 `connectNulls` 兜底。

决策记录：≤31 天用天（在最初"≤14"建议上放宽，因为有滚动兜底、天粒度细节更实用）；周对齐周一与系统"本周"口径一致；月标签用 `YYYY-MM`（跨年清晰）。

**验证**：分桶纯函数经 node 单测（周一对齐、粒度阈值、跨月周求和、部分周求和）；界面以四种范围实测。
